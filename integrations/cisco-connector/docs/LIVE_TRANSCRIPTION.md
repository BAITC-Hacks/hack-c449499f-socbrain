# Распознавание во время встречи и имена участников

Проверено по справочникам Cisco 23.09.2026.

**Да, можно построить локальную расшифровку во время встречи и использовать имена подключений.**
Для этого к аудио нужно добавить события CMS и потоковый ASR. Этот репозиторий пока реализует
запись и передачу завершённого файла; описанное ниже — схема следующего этапа, не готовая функция.

## Что даёт Cisco

[Events Guide 3.12+](https://www.cisco.com/c/dam/en/us/td/docs/conferencing/ciscoMeetingServer/Reference_Guides/Version-3-12/Cisco-Meeting-Server-Events-Guide-3-12.pdf)
описывает ресурс `callRoster`, в котором доступны `name`, `uri`, `state`, `activeSpeaker`.
Можно получать изменения состава и того, кто считается активным говорящим, через Events API.
Имена являются отображаемыми именами подключений, а не верифицированными ФИО.

## Предлагаемая обработка

```text
SIP-аудио → короткие PCM-фрагменты → локальный ASR → текст с временными метками
CMS Events → участники + activeSpeaker → временная шкала говорящих
Текст + шкала → предполагаемое имя + уверенность → приложение
```

Текст можно показывать с небольшой задержкой, зависящей от размера фрагмента, модели,
языка и CPU/GPU. Достижимую задержку и качество RU/KZ нужно измерить на вашем оборудовании.
Смешанную речь и границы реплик полезно уточнять диаризацией по завершении встречи.

## Почему имя не всегда можно подставить однозначно

- Один терминал переговорной может представлять нескольких людей.
- Несколько участников могут говорить одновременно; activeSpeaker не разделяет их звук.
- События и аудио приходят с разными задержками; временные шкалы надо синхронизировать.
- Пользователь может сменить отображаемое имя, подключиться дважды или без имени.
- SIP-ассистент в текущей реализации получает один входящий аудиомикс.

Поэтому результат следует хранить как `speaker_candidate` с источником `cms_active_speaker`
и показателем уверенности, а при неоднозначности оставлять «Говорящий 1»/«Не определён».
Нельзя считать список имён готовым соответствием голосам без проверки событий.
Для независимых дорожек каждого участника нужна отдельно подтверждённая медиаинтеграция;
обычные REST-запросы Call Bridge таких аудиофайлов не возвращают.

Следующий этап разработки: подписка на Events API, разбиение PCM, локальный ASR,
согласование времени, передача промежуточных сегментов и интерфейс исправления имён.
