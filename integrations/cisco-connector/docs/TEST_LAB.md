# Тестовый стенд Cisco Meeting Server

## Cisco dCloud

На 23.09.2026 найден официальный анонс
[Cisco Meeting Server 3.7 Demo v1](https://dcloud-docs.cisco.com/c/r/dcloud-docs/sites/en_us/news/cisco-meeting-server-3-7-demo-v1.html),
опубликованный в апреле 2023 года. Он подтверждает существование демонстрации CMS,
но не подтверждает, что сегодня её можно забронировать с конкретного аккаунта.
Действующий экземпляр лаборатории для этого проекта ещё не получен.

1. Войдите в [Cisco dCloud](https://dcloud.cisco.com/) с аккаунтом Cisco.com.
2. В каталоге найдите `Cisco Meeting Server`; проверьте доступные версии и руководство выбранного стенда.
3. Убедитесь, что стенд предоставляет доступ к API CMS и SIP/RTP, а для календаря — к CMS Scheduler.
   Наличие Web App или календаря TMS само по себе не подтверждает наличие Scheduler API.
4. Забронируйте сессию. Если нужная лаборатория недоступна вашему аккаунту, запросите
   общую сессию у представителя или партнёра Cisco.
5. Подключитесь способом из руководства сессии. Не используйте адреса и пароли из старых примеров:
   берите параметры только из своей выделенной лаборатории.

Согласно [актуальному FAQ dCloud](https://content.ciscodcloud.com/us/en/home/support/help/faq.html),
доступ зависит от уровня аккаунта; сотрудники и партнёры Cisco могут делиться сессиями.
Для подключения к лабораторной сети предусмотрены VPN/AnyConnect и другие способы,
указанные в руководстве конкретного стенда. Обычная сессия ограничена пятью днями.

## Приёмочная проверка коннектора

Используйте выделенную тестовую комнату и тестовых участников, уведомлённых о записи.
Параметры сохраняйте в локальном `.env`, сертификат CA — в `certs`.

1. Укажите `CMS_URL`, учётную запись API и доверенный CA. Выполните
   `docker compose exec connector python -m meeting_gateway.check`.
2. Через `/api/cms/spaces` и `/api/cms/calls` проверьте чтение комнаты и активного вызова.
3. Укажите отдельный `CMS_SCHEDULER_URL` и его учётные данные, если они нужны.
   Создайте тестовую встречу и проверьте её время и UUID комнаты через `/api/cms/schedule`.
   Если Scheduler отсутствует, автоматизация по расписанию этим тестом не проверена.
4. Разместите SIP-worker на Linux-хосте, от которого достижимы CMS/SBC и обратно проходят RTP-пакеты.
   Настройте SIP по [CISCO_SETUP.md](CISCO_SETUP.md), разрешите только тестовую комнату
   в `ASSISTANT_SPACES`, включите ассистента после уведомления участников.
5. Проверьте появление участника с отметкой `[REC]`, поступление аудио и завершение WAV.
   Статус принятой команды API или подключённый SIP-вызов без RTP не считаются успешной записью.
6. Настройте [приёмник SOCBrain](../../../backend/INGEST.md) и проверьте переход задания
   `/api/assistant/jobs` в `delivered`, затем получение записи по возвращённому `result.id`.
7. С заранее установленной локальной моделью запустите STT-worker и дождитесь `done`
   в `/api/recordings/{id}`; проверьте текст на тестовой фразе.
8. Отдельно проверьте отменённую встречу, повторную доставку и перезапуск worker.

Локальный `tests/sip_smoke.py` уже проверяет настоящий SIP/RTP с синтетическим тоном,
но не заменяет эту проверку Cisco. Имена говорящих и потоковая транскрибация пока
не реализованы; [LIVE_TRANSCRIPTION.md](LIVE_TRANSCRIPTION.md) описывает следующий этап.
